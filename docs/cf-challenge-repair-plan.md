# 网页验证与会话复用修复方案

日期：2026-10-28。状态：2026-10-29 已实施通用修复并完成 Node 与 API 26 受控设备验收；真实站点、可信 HTTPS 与完整 UI 矩阵仍待完成。详见 [实施与验收记录](cf-challenge-repair-validation.md)。

依据：[能力缺口核查](cf-challenge-gap-review.md)。目标是在现有搜索、发现、设置页及验证流程中，可靠地完成用户主动验证并复用有效会话，同时准确区分失败原因。

## 一、实施范围与原则

- 修复已确认的设置页网页宿主缺口；明确网页宿主的注册、归属、恢复和取消行为。
- 修复错误归类和调试信息，让抓取成功、网站响应成功、用户完成操作和实际通过验证各有依据。
- 验证并处理 API 26 第一方分区 Cookie 的读取与请求复用；兼容最低 API 20。
- 统一同一次操作在原生 HTTP、隐藏抓取 WebView、可见验证页中的有效 UA。
- 保留搜索/发现不自动弹网页、用户点“去验证”后重试的交互。脚本 HTTP 默认不自动触发验证的契约保持兼容。
- 本轮不实现无页面常驻 WebView、无人值守过盾、通用 403 自动浏览器回退或无限自动重试。
- 不预设两个案例已经定位到唯一根因，不承诺支持全部 Cloudflare 站点。
- 按功能拆分主应用和引擎提交。实施前重新记录两仓库状态，保留现有阅读缓存等工作区改动；本方案不改这些业务。

## 二、交付顺序

| 批次 | 内容 | 完成条件 | 依赖 |
| --- | --- | --- | --- |
| A：确定性修复 | 设置页宿主生命周期、请求取消、结构化错误及抓取状态说明 | 受控页面在设置页和搜索/发现可抓取；返回页面后可继续请求；错误阶段准确 | 无 |
| B：会话复用 | Cookie 对照实验、条件性分区读取修复、自定义 UA 对齐 | 有设备证据证明读取和发送符合预期；旧 API 不调用新签名；UA 服务端回显一致 | A 的诊断能力；UA 可独立实施 |
| C：交互与文档 | 登录/网页会话状态区分、脚本验证示例、完整最小测试源 | 完成操作不冒充登录或过盾；两种阶段都能按契约提示验证 | A、B |
| D：验收 | 受控设备矩阵、两个案例复查、构建安装与记录 | 通用能力通过验收；第三方成功/失败及证据单独记录 | A–C |

第一批即可独立交付；分区 Cookie 假设被否定时继续交付 A，不为验证假设引入无关改动。

## 三、A 批：网页宿主与失败定位

### A1. 设置页提供网页抓取宿主

涉及：`NativeSourceSettings.ets`、`WebBookFetchRuntimeHost.ets`、引擎 `WebBookFetchRuntime.ts`、`NativeSourceService.ts`。

- [x] 在设置页根容器内挂载现有隐藏抓取组件，不影响布局、触摸、滚动和无障碍焦点。
- [x] 页面数据可以先加载；需要网页的动作、动态选项、登录请求通过有界等待获取宿主。不要等待整个动态选项加载完成后才渲染宿主，避免相互等待。
- [ ] 补齐页面归属与恢复：进入设置页、打开验证页、返回设置页、返回主页后，应选择当前可用页面的抓取宿主；不能依赖上一个页面偶然存活。
- [ ] 运行时保存注册的控制器及其归属，注销当前控制器后可恢复仍有效的宿主；仅注册不表示可以执行，页面可见/恢复信号决定哪个宿主可接单。不得重新选择已销毁控制器。
- [x] 为设置页异步操作贯通取消信号；离开页面后取消其排队/活动请求并忽略迟到的 UI 更新，不取消其他页面所属请求。进入等待中的验证页应暂停原动作、返回后继续，不能把这一导航当成用户取消。
- [x] 宿主切换不刷新请求截止时间。不透明重放已开始的 POST 或带副作用请求；此类请求失去宿主后明确失败，由用户重新发起。允许迁移的安全读取仍遵守取消和总预算。

验收：冷进入设置页即执行 `browser.render`/`http.request({webView})`，动作中验证后继续抓取，返回主页再搜索，重复进入退出，队列中返回，慢页面超时；均不得出现悬挂任务、跨页面误取消或重复提交。

### A2. 用结构化字段保留真实失败阶段

涉及：引擎 `HttpClient.ts`、`WebBookFetchRuntime.ts`、`NativeSourceService.ts`、`NativeScriptHost.ts`、`NetworkErrorText.ts`、`BookSourceDebugModels.ts`，应用调试页。

- [x] 在内部响应上增加可选 `errorCode`、`errorStage`，并在响应转换、复制、重试和调试序列化中保留；原有 `error` 文本继续提供。
- [x] 至少区分：宿主不可用、等待宿主超时、网页队列超时、页面加载超时、选择器未满足、网页表达式失败、请求总预算耗尽、已取消、真实网络错误。
- [x] 结构化网页错误优先处理，不再经过泛化 timeout 正则后变成“连接服务器超时”。无法进一步归因的外层截止时间仅称“请求总等待超时”。
- [x] 调试记录补充宿主等待/排队/网页加载耗时和通道。按请求编号关联，日志不输出 Cookie、认证头或完整页面作为默认内容。
- [x] 增加内部及调试用 `statusCodeAvailable`，明确 WebView DOM 抓取未取得原始 HTTP 状态。为兼容现有脚本，暂保留 WebView 的成功 `status=200`，界面标为“网页抓取成功；原始 HTTP 状态未知”；`headersAvailable=false` 保持原义。

验收：同样的总超时在 HTTP、等待宿主、队列及 WebView 中能够正确说明；现有重试策略、脚本 `ok/status/error` 和取消行为不发生意外改变。

## 四、B 批：Cookie 与 UA

### B1. 先做可判定的 Cookie 实验

涉及：受控设备测试源/服务、本机 API 26 SDK、引擎 `CookieStore.ts`。

- [ ] 在可信 HTTPS 测试站点设置普通、HttpOnly、Secure 与 Partitioned Cookie；不使用关闭 TLS 校验的方式构造验收。
- [x] API 26 上比较 `fetchCookieSync(url, false)` 与 `fetchCookieSync(url, false, true)`；检查返回名称、数量和测试 Cookie 是否存在，不输出值。
- [ ] 同 URL 比较隐藏 WebView、可见 WebView、原生 HTTP 的发送结果，由受控服务端验证，不能仅依据客户端传输入参。
- [ ] 对真实站点完成一次用户主动验证后，检查 clearance 的存在性与两种读取方式差异；若并未得到 clearance，则先记录验证失败，不归咎于 Cookie 读取。

决策：如果设备证实分区 Cookie 可被新增签名读到，而旧读取/原生请求缺失，则实施 B2。若两种读取均无 Cookie，保留实验结果并继续调查验证是否完成、域/路径及分区归属，不宣称此假设成立。

### B2. 按用途读取第一方分区 Cookie

涉及：`CookieStore.ts`、`SourceEngineHost.ts` 的 Cookie 端口、`HttpClient.ts`、`NativeSourceService.ts`、`VerificationSupport.ts`、`VerifyWeb.ets`。

- [x] 将“为当前目标请求读取 Cookie”与“跨地址复制 Cookie”明确分开。API 26 第一方请求读取可包含该目标匹配的分区 Cookie；不一刀切改变所有旧调用者。
- [x] 原生书源 `cookie.get` 与原生 HTTP 请求使用同一匹配规则。若扩展 `SourceCookieJar`，采用兼容的可选能力；其他宿主不支持时保留原行为。
- [x] 通过系统 API 级别判断调用 API 26 签名；API 20–25 使用旧签名。只在已确认的能力不可用场景回退，其他失败留脱敏诊断。
- [x] 普通/分区同名 Cookie 的合并与顺序遵循 SDK 结果，不能简单转换成名字到值的 Map，破坏不同路径的 Cookie。
- [x] Cookie 仍由 ArkWeb 管理。不得把新增读取到的分区 Cookie 经 `copyCookies` 或镜像站同步转写成非分区 Cookie，也不得跨站复制 clearance。显式 Cookie 头与已有跨 origin 去凭据规则保持原有约束。
- [ ] 检查 `removeCookie`、`replaceCookies`、退出登录和清理会话是否能处理分区 Cookie。先核实可用 SDK 删除接口；若不能按站点可靠清除，明确记录限制，不用全局清空代替。
- [ ] 检查页面关闭、应用重启和过期后行为；区分浏览器会话 Cookie 与持久 Cookie，不额外承诺所有 Cookie 重启后保留。

验收：同站复用成功、不同站点不串用、不同路径结果正确、镜像域不携带复制的分区凭据、退出/过期后不继续读取旧状态；API 20–25 编译与运行兼容分开记录。

### B3. 同次验证采用一致的有效 UA

涉及：`NativeScriptHost.ts`、`NativeSourceRunner.ts`、`NativeSourceService.ts`、`NativeSourceInteraction.ts`、`AppSourceInteraction.ets`、`VerificationSupport.ts`、`VerifyWeb.ets`。

- [x] 复用原生书源已有请求头求值逻辑，避免验证页另写一套模板解释。大小写不同的 User-Agent 统一按同一优先级解析。
- [x] 自动提示验证时保存失败主请求已求值的有效 UA；显式 `browser.verify` 使用当前脚本上下文的有效 UA；设置页登录入口使用该源当前有效 UA。
- [x] UA 与书源、验证地址作为一次验证上下文绑定，路由携带上下文标识。不能只新增一个会被并发搜索覆盖的全局 UA 字段；选择其他待验证书源时也必须切换对应上下文。
- [x] 可见 WebView 首次加载前确定 UA，不能先用默认 UA 加载后再中途更换。无来源的普通网页入口沿用默认 UA。
- [x] 请求内临时覆盖 UA 的脚本，需有明确的验证传递方式；实施时增加可选参数并同步校验/桥接/文档，保持现有二参数 `browser.verify(url, hint)` 可用。只传 UA，不把整组认证头或 Cookie 暴露到路由参数。

验收：默认 UA、源级静态/动态 UA、单请求覆盖 UA、两书源不同 UA 并发提示验证及验证完成后重新请求；由受控服务端比较实际收到的 UA。

## 五、C 批：验证交互与书源契约

### C1. 区分账户登录与保存网页会话

涉及：`NativeSourceSettings.ets`、`NativeSourceService.ts`、`VerifyWeb.ets`、`VerificationSupport.ts`。

- [x] 设置页未声明登录判定且只有任意 Cookie 时，展示“已保存网页会话”，不直接称“已登录”。声明式登录检查、明确凭据或指定 Cookie 名的判断按各自契约处理。
- [x] 页面“完成”表示用户操作结束并保存会话，不等价于网站已经放行。只有后续业务请求拿到预期页面才确认可继续。
- [x] 网页验证使用不要求账户登录 Cookie 的模式；已有账户登录入口仍遵守登录要求。设置页提供清楚的“网页验证”入口，与账户登录目的区分，不要求用户伪造登录 Cookie 配置。
- [ ] 验证返回后更新会话显示及必要缓存；搜索/发现保留手动重试，操作中的 `browser.verify` 按原契约继续。取消不得提示成功。
- [x] 状态和入口使用现有主题语义色与材质；技术诊断留在调试页。

### C2. 补全脚本验证示例与诊断

涉及：引擎及应用书源开发文档、完整可导入测试源、调试报告。

- [x] 明确声明式主请求自动提示验证，脚本请求 `primary:false` 不自动改变控制流；不把所有脚本请求强制改为主请求。
- [x] 提供可导入示例：HTTP/网页请求识别挑战后调用 `browser.verify`；搜索/发现提示用户验证后重试，设置页按钮可等待用户完成后继续。
- [ ] HTTP 优先使用真实响应头/状态和页面特征共同判断；WebView 使用页面特征，`waitFor` 采用业务内容选择器。单独的 403、`body` 元素、`200` 或文中出现 Cloudflare 字样均不足以认定过盾/遇盾。
- [ ] 如需复用检测逻辑，先收敛现有 `VerificationSupport` 的判断和测试；不引入按站点名称硬编码的成功规则。
- [x] 调试结果增加脚本返回、有效记录、去重/相关性过滤及最终展示条数的分阶段统计，明确哪些属于引擎输出、哪些属于 UI 搜索策略。
- [x] 最小源必须包含真实可用的 login/actions/js 引用、搜索和发现配置及建议关键词；把 HTTP 与 WebView 两种路径作为独立用例，不再用缺字段片段推断 UI 差异。

## 六、验收矩阵

| 层次 | 用例 | 通过标准 |
| --- | --- | --- |
| Node：运行时 | 宿主注册/恢复、销毁、导航、取消、排队及总截止时间 | 无悬挂、无失效控制器接单、不扩大预算、不重放副作用请求 |
| Node：错误链路 | 每种错误穿过 HTTP → 原生服务 → 脚本/调试序列化 | 类型/阶段保留，不误标连接超时 |
| Node：Cookie | API 版本分支、读取用途、同名 Cookie、复制/清除边界 | 低版本不调用新 API，新增分区凭据不跨域复制 |
| Node：UA 与交互 | 三类 UA 优先级、验证上下文隔离、取消、登录显示 | 不串源，旧脚本调用兼容，未验证不冒充成功 |
| 真机：设置页 | 冷进入、动态选项、动作、验证往返、离页及重入 | HTTP/WebView/render 均能按需执行，页面返回后可继续 |
| 真机：搜索/发现 | 声明式及脚本两种模式、提示→主动验证→重试 | 不自动弹窗，状态可解释，业务结果能正常展示 |
| 真机：会话 | HTTPS HttpOnly/Partitioned、实际请求回显、重启/过期/退出 | 读取与发送证据一致，无跨站复用或残留误报 |
| 真机：真实站点 | 霹雳与刺猬、同关键词 UI/调试对照 | 分别记录成功或剩余阻碍，不用一个站点代表全部站点 |

复用已有 `native-script-check.mjs`、`native-source-check.mjs`、`network-compatibility-check.mjs`、`web-request-deadline-check.mjs` 及现有设备 fixture，按修改补充针对性断言。无需为文案和布局逐项新增脆弱的源码匹配测试。

构建前阅读 `docs/local-device-development.md`，使用 `node scripts/local-device-build.cjs --install`，显式设置 `LEGADO_DEVICE_TARGET=127.0.0.1:33761`，按项目规定清除当前进程代理设置；同步主应用、书源引擎、AI 引擎及已有工作区改动。记录构建、签名、安装、启动与进程检查结果，不保存签名秘密。

仅有 API 26 设备时，API 20–25 的模拟/静态兼容检查与实际设备验收分别列出，不标成低版本真机已通过。真实书源材料未取得时，可以完成受控矩阵，但不得将案例级修复标记完成。

## 七、完成定义与回退

- [ ] 设置页及页面往返不会因缺少有效宿主而无故失败；无页面场景返回明确的能力不可用信息。
- [ ] 各种超时能够定位到实际阶段；WebView 不把合成 200 展示成网站原始响应。
- [ ] UA 在同次验证流程中一致；Cookie 修复有受控设备证据，跨域与清理行为通过检查。
- [ ] 搜索/发现、账户登录与网页验证的既有可用流程没有回归。
- [ ] 更新开发文档、完整测试源和独立验收记录，区分受控通过、真实站点通过及未完成项目。

A/B/C 各批拆分提交，主应用与引擎兼容变更成组记录。发现 Cookie 行为回归时可独立撤回分区读取策略，保留宿主、诊断和 UA 修复；回退不清空用户全部会话，也不修改网络全局设置。
